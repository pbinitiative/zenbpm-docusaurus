# ZenBPM – v1.9.0

## Features
- Added job-level retries and configurable backoff:
  - retry counts and backoff policies through `zenbpm:taskDefinition`, including FEEL expressions,
  - worker overrides through REST, gRPC, and Go `WorkerError`,
  - automatic redelivery after backoff, with incidents created only when attempts are exhausted,
  - persisted attempt counts, failure history, and links between job incidents and their jobs,
  - retry management through `POST /v1/jobs/{jobKey}/retries` and failure history through `GET /v1/jobs/{jobKey}/failures`,
  - optional retry overrides when resolving an incident.
- Added configurable job locks per subscription:
  - `lock_duration_ms` and `max_active_jobs` settings per job type,
  - lock deadlines in gRPC job deliveries,
  - lock extension through gRPC and `POST /v1/jobs/{jobKey}/extend-lock`,
  - Go client options for lock duration and active-job limits, with explicit lock-renewal methods,
  - configurable server defaults and caps through the `jobManager` configuration section.
- Added static task headers through both `zenbpm:taskHeaders` and `zeebe:taskHeaders`. Headers are persisted with jobs and exposed through REST, gRPC worker messages, and inline handlers.
- Added automatic recovery of durable `Running` tokens after interrupted process execution. Recovery supports startup scans, periodic reconciliation, targeted wakeups, configurable batch sizes and grace periods, and exponential backoff after technical failures.
- Added cluster-wide allocation of BPMN definition keys and numeric versions. Concurrent deployments now receive consistent identities across partitions, and repeated deployments reuse the latest matching allocation.
- Added retry and reconciliation observability, including retry counters, backoff histograms, recovery outcomes, scan duration, queue depths, and retry-related tracing attributes.
- Updated core dependencies, including rqlite **10.5.1**, HashiCorp Raft **1.8.0**, gRPC **1.84.0**, OpenTelemetry **1.47.0**, and Prometheus client **1.25.0**.

## Fixes
- Fixed REST job-state filtering: requests for `terminated` jobs now return terminated jobs, and `failed` is accepted instead of returning HTTP 400.
- Repeated job completion now succeeds for already completed jobs and can resume stranded process execution without applying the completion twice.
- Job mutations now reload state under the process-instance lock, preventing concurrent assignment, failure, completion, or retry updates from overwriting newer state.
- Added delivery-token validation for worker failures. Repeated reports for the same delivery no longer consume additional attempts, and failures from superseded deliveries cannot affect the current delivery.
- Cluster restore now rebuilds the deployment-allocation registry from restored definitions. Deployment requests observed before a restore are rejected and retried against the restored state.
- Improved synchronization of engine startup, shutdown, timer management, and reconciliation to prevent background-manager lifecycle races.
- Updated job, configuration, cluster, and Go client documentation. Removed obsolete Script Engine and zenctl pages and outdated implementation plans.

## Breaking Changes
- The active-job limit is now counted per client **and job type**, rather than per client across all subscribed types. The default remains `10` for each type, so workers subscribed to multiple types may receive more jobs concurrently. Set `max_active_jobs` per subscription to control the total; limits are enforced independently by each partition leader.
- BPMN `retries` and `retryBackoff` settings are now enforced. Technical failures without an `errorCode` may leave jobs active until their next attempt, and intermediate failure variables are discarded. The default remains one attempt, preserving immediate incident creation unless retries are configured. Invalid literal retry settings are rejected during deployment.
- Completing a terminated or failed job, or failing a job that no longer waits for a worker, now returns HTTP `409`. Already completed jobs return success when completed again. Update clients that rely on the previous error responses.
- Go API signatures changed: `Engine.JobFailByKey` now requires retry-count, retry-backoff, and delivery-token arguments; pass `nil` to use default behavior. Generated REST client methods `ResolveIncident` and `ResolveIncidentWithResponse` now require a request-body argument; pass an empty `ResolveIncidentJSONRequestBody` for the previous behavior.
- Custom Go storage implementations must implement `FindRunningTokensAfter`, `FindRecoverableRunningTokens`, `FindJobFailures`, `HasJobFailureOfDelivery`, and `SaveJobFailure`, and persist the expanded job and incident fields. Pending-job queries must include failed jobs, while activation queries must exclude jobs waiting out retry backoff.
- Initial activation of cluster-wide deployment allocation requires every Raft member to announce support for the new protocol. Deployments are refused until all members support it. After activation, incompatible binaries cannot join, and downgrading an existing member while retaining its data is unsupported.
- Failed BPMN deployments now reserve their version tags even if no partition persisted the definition. Retry the original content to finish the deployment, or use a new tag for changed content. `alreadyExisted` reflects allocation identity and does not prove that an earlier deployment completed successfully.
- Building from source now requires Go **1.26.7** or newer.
